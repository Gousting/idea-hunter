# idea-hunter

独立开发者需求挖掘流水线。**零第三方 Python 依赖**（纯标准库），可直接跑。

> ⚠️ 注意"零依赖"的确切含义：**Python 侧**确实零依赖。但要跑出 `out/latest_*` 里
> 那份质量，还需要下面「真实前置条件」里的几样外部件 —— 否则漏斗会大幅塌缩。

两个入口：

| 入口 | 定位 | 用途 | 产出 |
|---|---|---|---|
| `run_windows.py` | **主线**（推荐） | 按时效性输出「值得看的方向」Top10（今日/本周/本月） | `out/directions_*.md` |
| `run.py` | 旧轨道，保留 | 单次深度采集 + 规则过滤 + LLM 打分 | `out/report_*.md` |

> `run.py` 自 2026-09-17 起未再更新，实际已被 `run_windows.py` 取代。两者定位不同
> （前者有持久化冷却去重，后者不做去重、定位是"随时跑一次看当下"），所以都保留，
> 但**新读者请从 `run_windows.py` 开始**。

完整方案与实测数据见 **[方案_需求挖掘流水线可行性.md](./方案_需求挖掘流水线可行性.md)**。

## 真实前置条件（决定产出质量，务必先读）

跑通链路 ≠ 跑出可用产出。两者的差距全在下面这张表：

| 前置件 | 缺了会怎样 | 怎么补 |
|---|---|---|
| `GITHUB_TOKEN` | 核心接口未认证仅 60 次/时**且按 IP 共享**，一轮三窗口要发 ~35 次查询 → 拥挤度/成型数大面积失败 | 建一个 PAT 并 export |
| 本地代理 | Reddit 在国内网络不可达（实测非 headless 识别，是 ASN 段级封锁） | `HUNTER_PROXY`，或让脚本自动探测 7897/7890/… |
| Chrome + OpenCLI 扩展 + `npm i -g @jackwener/opencli` | **丢 4/6 项能力**：付费需求、创始人原话、中文需求、新发布产品 —— 实测能力缺口从 0% 变 **67%**，方向数从 17 掉到 7，付费信号列全 0 | 见下方「OpenCLI 通道」 |
| `DEEPSEEK_API_KEY` | 降级为关键词签名（语义分类失效）。**降级模式只用于验证链路，不能用于选品** | export 即可 |

CLI 定位已改为可移植（环境变量 `OPENCLI_BIN` > PATH > 常见局部安装位置 > `npx` 兜底），
不再依赖任何机器专属路径。

## 方向聚合（run_windows.py）

用户要的不是"12 条帖子"，而是"哪些方向值得看"。所以这一层把散点候选聚合成方向：

- **判定口径**：一个方向必须在本时间窗内出现 **≥2 条独立证据**。单条提及不算方向。
- **打分（热度）**：证据数×1.0 + 信源多样性×0.8 + 付费信号×1.2 + 仓库热度×1.5 + 仓库数×0.4
- **拥挤度（供给）**：对热度 Top12 方向，查 GitHub 同关键词**存量项目数**（`stars:>50` 只算真项目），按实测分布分级：**红海≥1000 / 拥挤≥300 / 中等≥80 / 稀疏<80**
- **机会象限**：高热度 + 低拥挤 =「★ 值得看」；高热度 + 红海 =「已拥挤：需差异化切入」；报告末尾有汇总
- **机会分**：热度分 ÷ log10(存量+10)——越拥挤，机会被稀释得越厉害
- **跨窗口观察**：三个窗口都出现的方向更接近持续需求；只在单一窗口出现多是短期热点。
- **分类方式**：人工维护的方向关键词签名，不用无监督聚类——几百条短文本上聚类产物不稳定、方向名不可读，而"独立开发者能做的方向"本身有限可枚举。
- **时间窗口映射**：GitHub `since=daily/weekly/monthly` + `created:>1d/7d/30d`；HN `created_at_i` 过滤；Reddit 用 OpenCLI 的 `--sort/--time`（无 OpenCLI 时退回 RSS）。
- **注意**：`min_stars` 必须随窗口缩放（`created:>1d stars:>60` 实测返回 0 条）。

参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--windows` | `day,week,month` | 要跑的窗口 |
| `--no-reddit` | — | 跳过 Reddit（省约 2 分钟） |
| `--top` | 10 | 每个窗口输出几个方向 |
| `--min-evidence` | 1 | 进入榜单的最少证据数。默认 1 —— 不隐藏弱信号，而是用「证据强度」列标出来 |
| `--from-cache` | — | **复用已采集数据只重跑聚合**（留空取最新缓存）。调阈值/改分类时用，实测 391s → 0s |

**为什么不做"必须 ≥2 条证据"的硬门槛**：实测会把输出压到只剩 4–5 个方向（一个窗口规则层只留 60 多条，摊到 28 个方向后多数只有 1 条）。与其假装凑满 10 个，不如全量排序并显式标注强度，让弱信号以本来的面目出现。

**已知局限**：关键词分类会有误判（实测有约 38–60% 的候选匹配不到任何方向，也有个别误分）。这是关键词方案的固有上限，不是 bug；要靠 LLM 才能根本解决。

## OpenCLI 通道（推荐：直接用你已登录的 Chrome）

**这是目前能力最强的一条通道**，因为它复用你正在用的 Chrome 登录态，能拿到官方 API 与 RSS 都拿不到的东西。

```bash
# 前提：Chrome 保持打开，OpenCLI 扩展已启用
python run_windows.py --opencli          # 三窗口，含 Reddit / Upwork / Product Hunt
python hunter/opencli.py                 # 自检：代理、CLI、公开适配器
python hunter/opencli.py --with-browser  # 自检：含需登录的适配器
```

**安装**：扩展本体已装（ID `ildkmabpimmkaediidaifkhjpohdnifk`，与官方商店一致）。
CLI 本体用 `npm install @jackwener/opencli` 装在隔离工作区，无需全局安装。

**实测要点（都踩过）**：

1. **CLI 的 Node 进程不走系统代理** —— 不加 `HTTP_PROXY` 会连 Google 地址超时（实测 `34.120.x.x:443 timeout`）。本模块会自动探测本地代理端口并注入。
2. **`[public]` 适配器不需要浏览器，`[cookie]` 适配器必须 Chrome 打开**，否则返回 `exitCode 69 / BROWSER_CONNECT`。
3. **不要为了读 cookie 而关闭 Chrome** —— OpenCLI 走"扩展 + 守护进程"，本来就不需要复制 cookie（这是我一开始判断错的地方）。
4. **`upwork` 没有 `--limit`**，用 `--per_page`（10–50，仅支持单页）；传错参数直接报 `unknown option`。
5. **`reddit subreddit` 支持 `--sort hot|new|top` 与 `--time hour|day|week|month|year|all`** —— 所以三个时间窗都能直接表达，比 RSS 更强；`reddit read <url>` 还能拿到**评论**。

**内置适配器共 177 个**，与我们相关的有：`reddit`（含 `read` 评论）、`producthunt`、**`upwork`**（正在付钱找人做的事 = 付费意愿最硬的证据）、`twitter`、`hackernews`（`ask`/`show`/`jobs`）、`xiaohongshu`、`zhihu`、`v2ex`、`weibo`、`medium`、`substack`、`stackoverflow`、`lobsters`、`devto`、`lesswrong`、`indeed`、`1point3acres`、`36kr`。

信源预筛权重（OpenCLI 相关）：`upwork 3.4 > reddit 2.6 > producthunt 2.2`。



## 备用方案：复制登录态（已被 OpenCLI 通道取代，保留以备 OpenCLI 不可用时使用）

**注意：如果 OpenCLI 可用，不要走这条**——它需要关闭 Chrome，而 OpenCLI 不需要，且 OpenCLI 能拿到评论。
仅当 OpenCLI 的扩展/守护进程出问题时，才用这条退路：

Reddit 的 RSS 只有帖子正文、**没有评论**，而评论才是抱怨最集中的地方。要用 HTML + 评论，必须带登录态：

```bash
# 1. 完全退出 Chrome（含后台进程）——运行中 cookie 库被独占锁定
# 2. 复制登录态到独立调试目录
python hunter/browser.py login-setup
# 3. 检查各站点登录情况
python hunter/browser.py login-check
# 4. 读 Reddit 帖子页（含评论）
python hunter/browser.py reddit --sub SaaS

# 5. 用完后清理复制出来的 cookie
```

说明：

- `opencli` **在 npm 上不存在**（唯一出处是 openclaw 的技能市场，无公开分发包），所以无法安装。但它的核心能力（复用 Chrome 登录态）用本机已装的 `browser-use` 同样能实现。
- Chrome 136+ 出于防 cookie 窃取，禁止在默认 user-data-dir 上开远程调试，因此必须复制到独立目录。
- 只复制维持登录的最小文件集（`Local State` + `Default/Network/Cookies` + `Preferences` + `Login Data`），**不复制书签、历史、扩展数据**。
- 脚本只读取 cookie 的 `host_key` 与条数，**不解密任何值**。

## 设计要点（踩过的坑）

1. **供给 ≠ 需求，分两个队列。** 仓库简介不是需求证据，它只是待挖掘对象；需求必须来自 Issues 里的用户原话。
2. **深挖对象要选"有 issue 积累"的项目**，不是最新最火的。实测按"最新"挑 4 个仓库，全部返回 0 条。
3. **正则只是降噪器，不是闸门。** 把 issue 采集设成"必须命中关键词"会让召回塌成 0。
4. **需求侧门槛必须用第一人称购买构式**，裸词面（`willing to pay`）的精度约等于 0。
5. **HN Algolia 多词是 AND 语义。** `docker` 9.8 万条 → `docker painful` 890 条。用短查询扇出，别写自然语言长句。
6. **冷却去重，不是永久去重。** 永久去重会让日更流水线第二天拿到空列表。
7. **LLM 必须有证据引用闸门。** 引用不出原文的结论一律作废。
8. **LLM 预算要按信源配额分配。** 只按全局分数排，HN 会靠条数把预算全占掉（实测 top12 全是 HN，质量更高的通道 0 条）。改为每源保底 2 条后，Indie Hackers 记录才进得来。
9. **浏览器通道读不到 Cloudflare 站点，也绕过不了网络层封锁。** Product Hunt / V2EX 返回验证页；Reddit 返回 `Blocked`（本机出口为国内宽带 IP，Reddit 在国内网络不可达）。被拦截必须显式报错，不能当成"没有数据"。
10. **Reddit 要走 RSS，不要走 HTML。** HTML 403（ASN 段级封锁，换节点无效）；`.rss` 端点 200。注意限流极紧，间隔 22 秒起。
11. **跨子版块重复要按标题去重。** Reddit 交叉发帖的 `t3_` id 不同，`source_id` 去重拦不住。
12. **话题域门槛只能看帖子标题，不能把评论正文一起传。** 正文里几乎必然出现某个技术词，传进去等于没门槛（实测"出生率辩论"就是这么漏的）。

## Reddit 通道（走本地代理 + RSS）

```bash
python run.py --reddit --reddit-subs SaaS,microsaas,SideProject
```

代理自动探测（`HUNTER_PROXY` > 7897 > 7890 > 10809 > 1080），也可显式指定：

```bash
export HUNTER_PROXY=http://127.0.0.1:7897
```

实测要点：

- **HTML 页面全部 403**（`network policy` 拦截），且实测 14 个节点返回体长度完全一致 → **封的是整个 ASN 段，换节点无用，不要在这上面浪费时间**
- **RSS 端点可用**：`https://www.reddit.com/r/<sub>/.rss` → 200
- RSS 硬约束：每版块最多 25 条、**只有帖子正文没有评论**、限流极紧（429 后约 45–90 秒恢复）
- 因此：请求间隔 22 秒、单次不超过 4 个子版块
- 合规定位：官方公开订阅端点、低频低量、个人研究用途；不对外分发、不产品化

## 客户线索（`tools/leads.py`）—— 另一条用法

`run_windows.py` 把线索**聚合成方向**，回答"什么值得做"。
但如果你缺的不是"做什么"而是"谁能付钱"，聚合恰恰把最有用的信息压扁了：
报告里每个方向只展示 3 条证据，金额、原文、联系人全被丢掉。

`leads.py` 反过来做 —— **保留线索的个体身份**，回答"现在能接哪个活"：

```bash
python tools/leads.py                       # 全通道采集（需 Chrome + OpenCLI）
python tools/leads.py --from-cache          # 只从已有 window_cache 抽（离线、秒出）
python tools/leads.py --sources zhihu,v2ex,forhire,bounty
python tools/leads.py --min-score 4         # 只看值得联系的
```

产出 `out/leads_*.md`：**谁 / 要做什么 / 预算多少 / 原文 / 怎么联系 / 值不值得联系**。

### 通道（实测）

| 通道 | 命令 | 需登录 | 说明 |
|---|---|---|---|
| V2EX 外包 | `v2ex node outsourcing` | 否 | **国内最接近 r/forhire 的入口**（酷工作节点是 `jobs`） |
| 知乎搜索 | `zhihu search <q>` | 否 | 实测有效，能直接捞到「有偿寻找…」类需求 |
| 小红书搜索 | `xiaohongshu search <q>` | 否 | 搜索免登录；部分查询会超时，属正常 |
| GitHub 赏金 | 复用 `hunter/sources.py` | 否 | 金额写在 issue 里 |
| r/forhire | 复用 `hunter/sources.py` | 否 | 只取 `[Hiring]`，`[For Hire]` 已过滤 |

> 注：36kr 不适合（是媒体站，搜"外包"返回 0 条）；Upwork 需登录且适配器侧常失败。

### 三项判据 + 两道选样 + 四道过滤

打分：**钱** × 1.5 ＋ **需求具体度** × 1.0 ＋ **新鲜度** × 1.0。

**「钱」按量级给分，不是看有没有**（踩过的坑）：原实现只看"有没有金额"，
于是 `$50/week` 的营销零工和 `$3000` 的悬赏拿同样的分、并排在最前面 ——
实测榜单前 12 条里有 4 条是 `$18/h`、`$50/week` 这类低价值零工。

三种计价方式用三把尺子（阈值按"这算不算一个正经的付费委托"定，不是按绝对值）：

| 计价方式 | 3 分 | 2 分 | 1 分 |
|---|---|---|---|
| 一次性 | ≥500 | ≥150 | <150 |
| 时薪 | ≥50/h | ≥20/h | <20/h |
| 周期价 | 月均 ≥1500 | ≥500 | <500 |

所以 `$3000` 悬赏 → 3，`$800` 脚本 → 3，`$20/h` → 2，`$18/h` → 1，
`$50/week`（≈200/月）→ 1。

> 已知局限：**不区分币种**，500 元与 $500 同等对待 —— 会低估人民币小额单、
> 高估美元小额单。要精确得引入汇率，对"排序"这个用途不值当。

四道过滤，缺一不可（每条都对应一次实测踩坑）：

| 过滤 | 防的是什么 |
|---|---|
| 供给方过滤（中英双词表） | 「个人纯手工接单，脚本定制」这类**方向相反**的帖子。实测知乎搜"有偿找人做脚本"，前 2 条就有 1 条是供给方 —— 与 `hunter/filter.py` 的 `[Hiring]` vs `[For Hire]` 是同一类错误 |
| 金额合理性 | `$239398281948585883`（18 位 issue id）被当成钱 → 26 条垃圾把 top30 挤满 |
| 标题质量 | 「[Bounty] Bounty」「EKEODKDE9DKE9DO BOUNTY」这类占位/刷量 issue：标题没信息但正文凑得出金额 |
| 同源主体上限 2 条 + 信源配额保底 3 条 | 单个刷量仓库连发 6+ 条；以及条数多的信源霸榜（**这是项目在 P0-3 学到的教训**："信源配额是防止『劣币驱逐良币』的必要机制"） |

### 二段式深读（`--deep-n`，默认 8）

**问题**：知乎/小红书的**搜索结果不含正文**，只有标题 —— 于是「钱」和「具体」两列
对国内线索系统性偏低，而国内线索恰恰最需要。

**做法**：标题粗排（零成本）→ 对头部 N 条深读正文 → 重打分。顺序很重要：
配额先决定"谁有资格被看见"，深读再补上标题里没有的信息。

| 来源 | URL 形式 | 深读命令 | 状态 |
|---|---|---|---|
| V2EX | `/t/<id>` | `v2ex topic <id>` | ✅ |
| 知乎 | `/question/<qid>/answer/<aid>` | `zhihu answer-detail <url>` | ✅ 附带 `created_at` |
| 知乎 | `/question/<qid>` | `zhihu question <qid>` | ✅ |
| 知乎 | `/p/<id>`（专栏文章） | 无对应命令 | ❌ |
| 小红书 | `search_result` / `explore` | — | ❌ Navigation rejected（需登录） |

深读返回体里的 `created_at` 会顺手补上原本缺失的新鲜度。

> **深读的真实价值**（实测）：一条标题看着像需求的知乎回答，正文是
> 「简单点，淘宝直接搜脚本编辑」—— **不是需求，是建议。只有读了正文才知道。**

### 应征话术（`--scripts`，默认 3）

线索表解决"有没有活"，但真正让人卡住的是**打开对话框不知道写什么**。
对不擅长主动推销的人，这个门槛比"找不到活"更高 —— 所以产出里直接附上可复制的话术。

**四类线索四套模板**（语气和问题完全不同）：

| 类型 | 语气 | 问什么 |
|---|---|---|
| 悬赏/赏金 | 技术方案式 | 复现条件、什么算完成（合并 PR / 通过测试） |
| 招聘 | 求职式 | 是否接受远程兼职、团队与技术栈、面试流程 |
| 询价 | 给判断框架 | 不问技术细节，给定价维度（进入候选名单比拿下这单重要） |
| 外包需求 | 项目式 | 具体技术问题 + 交付形式与验收标准 |

三条写法原则（从"对方会怎么读"倒推）：**① 引用他的原话证明你读懂了**，
而不是群发自我介绍；**② 问具体的技术问题**，问对问题本身就是能力证明；
**③ 主动给"先出方案再决定"的台阶**，降低对方决策成本，也降低你的承诺风险。

> 类型判断错了，话术还不如不写 —— 实测踩过：第一版只有一套"项目式"模板，
> 对一条「量化策略研究员」招聘帖写「这个我可以做」、还问它「跑在什么环境」，
> 错位得非常明显，一眼能看出是模板群发。

### 能力画像（`--mark` / `--profile` / `--use-profile`）

**这一步不做，工具就只是个清单。**

```bash
# 1) 读一遍清单，对每条标一个「能做 / 不能做 / 想做」（序号是上表行号）
python tools/leads.py --mark 3:yes --mark 7:no --mark 11:maybe

# 2) 标够 5 条后看画像
python tools/leads.py --profile

# 3) 让后续榜单按画像把你能接的排前面
python tools/leads.py --use-profile
```

**为什么做这个**：这套工具解决的是"谁能付钱"，但使用者的真实困境往往是
**"我也不知道我能做什么"**。这是自我认知问题，工具无法替他回答 —— 但工具能提供证据。

标注的对象是**市场上真实存在的活**，所以画像不是心理测试，是**市场快照**：
结论直接可用（"这类活我能接，而且市场上每周有 N 条"），而不是自我感觉。

产出 `out/leads_profile.md`，给**逐类目对比 + 净信号**（能做 − 不能做）：

| 类目 | 能做 | 不能做 | 净信号 |
|---|---:|---:|---|
| 小程序 | 2 | 0 | ✅ 明显能做 |
| 脚本/自动化 | 1 | 1 | — 打平 |
| AI/模型工程 | 1 | 3 | ❌ 明显不能做 |

净差为 0 说明自己还没想清楚 —— 提示多标几条再下结论；样本不足时会明确写
**"别拿现在的结论去改简历"**。

台账（`out/lead_marks.json`）按 URL 累积、跨轮次保留，所以标得越久越准。

**已标注过的线索会自动沉到榜尾**（「上次」列显示上次的标记），
用 `--new-only` 则完全隐藏 —— 这样"每周跑一次、标 20 条"才跑得下去，
不用反复重读同样的东西。

> **`use-profile` 只加减分，不做硬过滤。** 硬过滤会形成信息茧房 ——
> 你今天标「不能做」的类目，可能正是三个月后你该做的那一类。

> 踩过的坑：台账原名 `leads_log.json`，也匹配取产出的 glob `leads_*.json`，
> 而它在字符串排序里排在 `leads_20260920-1029.json` **之后** ——
> 于是"取最新一轮产出"会读到台账本身，`--mark` 的序号全部错位（静默出错）。
> 现已改名 `lead_marks.json`，并把取产出的 glob 收紧为 `leads_[0-9]*.json`。

### 合规

抓的是公开页面，用途限定为**个人找活**；不要批量转发或做成对外产品。
登录态类通道（小红书 / Upwork）可能违反站点自动化条款，有账号风险 —— 见 `out/resilience.json` 的合规登记。

## 口径纪律与自检机制（2026-09-18 新增）

这套流水线的卖点是"口径诚实"，所以**声明式文案必须由数据生成**，不允许硬编码。
以下四条机制各自对应一次真实事故，`tests/test_pipeline.py` 里都有对应的回归测试：

| 机制 | 防的是什么（真实事故） |
|---|---|
| `paths.SOURCE_PATH` 显式登记 + 兜底取 `KEYWORD` | 原先兜底是 `PLATFORM`（原生榜=真独立发现）→ 新信源忘了声明就白拿原生身份，「原生榜贡献率 ≥40%」这个头条指标可以**自证达标**。现在漏登记只会让指标变保守，并在报告里被 `undeclared()` 列出来 |
| 报告里的「原生率的信源明细」 | 只给一个百分数没法审计。现在摊开每个信源的贡献，并单独标出**弱原生**（github_search 的 stars 门槛、reddit 的子版块清单、browser 的站点清单——排序由平台给，但入池范围由作者定） |
| 判定方式按**实际命中率**标注 + 覆盖率披露 | 原先只看"有没有传 `--annotations`"，传空 `{}` 也声称"agent-语义分类"，而榜单 100% 来自关键词签名。更糟的是同一次运行的**看板**说"关键词签名（含部分 agent 语义标注）"、**报告**说"agent-语义分类"——两份产出互相矛盾。现在两个渲染器共用同一口径 |
| 判断层复用 `filter.supply_risk()` | `tools/write_platform_analysis.py` 是手写散文，原先完全绕过 L2 反刷星。实测把 `jev-ultrafast`（★3564/2 天、fork/star 0.060、日均涨星 1314）称为"本轮最强爆发信号"，而项目自己的 L2 已判定它 high 并把它从方向报告丢掉了——**自动层拒绝、手写层推荐**。现在手写层必须过同一道体检，高危项会在报告顶部与条目内显著标注 |

另有两处产出层面的修复：报告里的口径警告改为**按本轮数据计算**（原先是硬编码字符串，
跑今日窗口时也照样输出"本周榜第一的 8 条证据…"）；「真实案例速查」的 Markdown 链接
改用半角 `)` 收尾（原先用全角括号，导致 30 处链接全部不可点击 —— 而那正是该章节存在的唯一理由）。

北极星指标已挪到**报告第一行**：按本项目的判据（"必须有验证闭环，否则产出等于零"），
它是全局最重要的状态，不该藏在末尾章节里。
